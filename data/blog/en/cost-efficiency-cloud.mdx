Nothing kills a startup faster than a surprise cloud bill. I've seen teams go from "cloud is so convenient" to "why is AWS charging us $50k this month" real fast.

The cloud is not expensive. Using it wrong is.

Let's talk about designing systems that scale without breaking the bank.

## The Cloud Pricing Model

First, understand how cloud providers make money:

```
How they price things:
  Compute:  Per hour/second of CPU running
  Storage:  Per GB stored per month
  Network:  Per GB transferred (egress is expensive!)
  Requests: Per API call (for serverless)

What catches people off guard:
  - Data transfer between regions: $$$
  - Data transfer out to internet: $$$
  - Data transfer to same region: often free
  - Idle resources: still paying full price
  - Over-provisioned instances: paying for capacity you don't use
```

## Right-Sizing: The Low-Hanging Fruit

Most companies overprovision by 30-50%. Right-sizing is free money.

```
Signs you're overpaying:
  - CPU average < 20%
  - Memory usage < 40%
  - "We provisioned for peak traffic" (that happens once a month)
  - Nobody ever looked at instance sizes after initial setup

Example savings:
  c5.4xlarge (16 vCPU, 32GB) → c5.xlarge (4 vCPU, 8GB)
  Before: $0.68/hour × 730 hours = $496/month
  After:  $0.17/hour × 730 hours = $124/month
  Savings: $372/month per instance

  10 instances = $3,720/month = $44,640/year
```

```python
# Simple script to find over-provisioned EC2 instances
import boto3
from datetime import datetime, timedelta

cloudwatch = boto3.client('cloudwatch')
ec2 = boto3.client('ec2')

def get_cpu_average(instance_id, days=14):
    response = cloudwatch.get_metric_statistics(
        Namespace='AWS/EC2',
        MetricName='CPUUtilization',
        Dimensions=[{'Name': 'InstanceId', 'Value': instance_id}],
        StartTime=datetime.utcnow() - timedelta(days=days),
        EndTime=datetime.utcnow(),
        Period=3600,
        Statistics=['Average']
    )
    if response['Datapoints']:
        return sum(d['Average'] for d in response['Datapoints']) / len(response['Datapoints'])
    return None

# Find instances with < 20% CPU utilization
instances = ec2.describe_instances()
for reservation in instances['Reservations']:
    for instance in reservation['Instances']:
        instance_id = instance['InstanceId']
        cpu = get_cpu_average(instance_id)
        if cpu and cpu < 20:
            print(f"{instance_id}: {cpu:.1f}% CPU - candidate for downsizing")
```

## Reserved Instances vs On-Demand vs Spot

Three pricing models, three use cases:

```
On-Demand (pay as you go):
  - Full price
  - No commitment
  - Best for: unpredictable workloads, testing

Reserved Instances (1-3 year commitment):
  - 30-60% discount
  - Commit to specific instance type and region
  - Best for: stable, predictable workloads

  Example:
    c5.xlarge On-Demand:  $0.17/hour = $1,241/year
    c5.xlarge 1yr RI:     $0.10/hour = $730/year (41% savings)
    c5.xlarge 3yr RI:     $0.07/hour = $511/year (59% savings)

Spot Instances (bid on spare capacity):
  - 60-90% discount
  - Can be terminated with 2 minute warning
  - Best for: fault-tolerant, stateless workloads

  Use cases:
    ✓ Batch processing
    ✓ CI/CD pipelines
    ✓ Dev/test environments
    ✓ Stateless web workers (with auto-scaling)
    ✗ Databases
    ✗ Single-instance production workloads
```

import requests
import time

def check_spot_termination():
    """Check if this spot instance is being terminated"""

        pass

def graceful_shutdown():
    """Clean up and drain connections"""

# Check every 5 seconds
while True:

## Serverless Economics

Serverless (Lambda, Cloud Functions) flips the cost model:

```
Traditional: Pay for servers running 24/7
Serverless:  Pay only when code executes

Break-even analysis:
  Lambda pricing: $0.20 per 1M requests + $0.0000166667/GB-second

  For a 128MB function running 100ms:
    Per request: $0.0000002 + $0.0000002083 = $0.0000004083

  1M requests/month = $0.41
  10M requests/month = $4.10
  100M requests/month = $41.00

  vs EC2 t3.micro ($7.59/month) handling same traffic

  Lambda is cheaper when:
    - Traffic is bursty
    - Many endpoints with low traffic each
    - You value not managing servers

  EC2 is cheaper when:
    - Consistent high traffic
    - Long-running processes
    - Need persistent connections (WebSockets)
```

### Cold Start Cost

Cold starts aren't just a latency problem, they cost money:

```
Cold start scenario:
  - Function initializes (2 seconds)
  - Function executes (100ms)
  - You're billed for 2.1 seconds

Warm scenario:
  - Function executes (100ms)
  - You're billed for 100ms

Solutions:
  1. Keep functions warm (scheduled pings)
  2. Provisioned concurrency (pay for guaranteed warm instances)
  3. Optimize initialization code
  4. Accept cold starts for non-critical paths
```

## Data Transfer: The Silent Killer

Data transfer costs sneak up on you:

```
AWS data transfer pricing (approximate):
  Same AZ:              Free
  Different AZ:         $0.01/GB
  Different region:     $0.02/GB
  Out to internet:      $0.09/GB
  CloudFront to users:  $0.085/GB (cheaper than direct!)

Example: Video streaming service
  1TB/day egress to users = 30TB/month
  Direct from S3:     30,000 GB × $0.09 = $2,700/month
  Via CloudFront:     30,000 GB × $0.085 = $2,550/month (and faster!)

  Better: Use CloudFront + enable compression
  Compressed (30% savings): 21,000 GB × $0.085 = $1,785/month
```

### Architectural Decisions That Reduce Transfer Costs

```
1. Keep compute close to data
   Bad:  S3 in us-east-1, compute in eu-west-1
   Good: S3 and compute in same region

2. Use VPC endpoints for AWS services
   Without: Traffic goes through internet (NAT gateway costs)
   With:    Traffic stays in AWS network (cheaper)

3. Compress everything
   Before: 1GB JSON response
   After:  100MB gzip response
   Savings: 90% on data transfer

4. Cache aggressively
   1M requests/day × 100KB response = 100GB/day
   With 80% cache hit rate = 20GB/day
   Savings: 80%

5. Consider multi-CDN or direct peering for high volume
   CloudFront: $0.085/GB
   Direct connect or dedicated bandwidth: much cheaper at scale
```

## Database Cost Optimization

Databases are often the biggest cost center:

```
RDS cost breakdown:
  - Instance hours (biggest chunk)
  - Storage (provisioned IOPS is expensive!)
  - Data transfer
  - Backups beyond free tier

Optimization strategies:

1. Use Aurora Serverless for variable workloads
   Traditional RDS: Pay for instance 24/7
   Aurora Serverless: Scale to zero when idle
   Great for: Dev/test, infrequent workloads

2. Read replicas instead of bigger instances
   Scale reads horizontally (cheaper than vertically)

3. Reserved instances for production databases
   Databases run 24/7 → perfect for RIs

4. Archive old data to S3
   RDS storage: $0.115/GB/month
   S3 Standard:  $0.023/GB/month
   S3 Glacier:   $0.004/GB/month
```

```python
# Example: Archive old data to S3
import boto3
from datetime import datetime, timedelta

def archive_old_records(cutoff_days=365):
    """Move records older than cutoff to S3, delete from RDS"""
    cutoff_date = datetime.now() - timedelta(days=cutoff_days)

    # Query old records
    old_records = db.query(
        "SELECT * FROM orders WHERE created_at < %s",
        [cutoff_date]
    )

    # Write to S3 (Parquet for compression)
    s3 = boto3.client('s3')
    s3.put_object(
        Bucket='my-archive-bucket',
        Key=f'orders/year={cutoff_date.year}/data.parquet',
        Body=to_parquet(old_records),
        StorageClass='GLACIER'  # Cheapest for archive
    )

    # Delete from RDS
    db.execute(
        "DELETE FROM orders WHERE created_at < %s",
        [cutoff_date]
    )
```

## Auto-Scaling Done Right

Auto-scaling saves money by matching capacity to demand:

```yaml
# Kubernetes HPA with cost-aware scaling
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: my-app-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: my-app
  minReplicas: 2
  maxReplicas: 50
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70  # Scale up at 70% (not 50%!)
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 300  # Wait 5 min before scaling down
      policies:
        - type: Percent
          value: 10  # Remove max 10% of pods per minute (gentle)
          periodSeconds: 60
    scaleUp:
      stabilizationWindowSeconds: 0  # Scale up immediately
      policies:
        - type: Percent
          value: 100  # Can double capacity quickly
          periodSeconds: 15
```

```
Common auto-scaling mistakes:

1. Too aggressive scale-down
   Problem: Pods removed, traffic increases, scale-up, repeat
   Cost: Constant churn, wasted resources on startup
   Fix: Longer stabilization window

2. Too conservative scale-up
   Problem: Latency increases during traffic spike
   Cost: Lost revenue, poor user experience
   Fix: Fast scale-up, slow scale-down

3. Scaling on wrong metric
   Bad: Scale on CPU for I/O-bound workload
   Good: Scale on request queue depth or latency
```

### Cost Allocation Tags

Tag everything. Seriously.

```
Required tags for every resource:
  - Environment: prod/staging/dev
  - Team: payments/orders/platform
  - Service: api/worker/database
  - CostCenter: engineering/marketing/operations

Benefits:
  - See cost per team
  - See cost per environment (dev is often 30% of prod!)
  - Identify orphaned resources (no owner tag = delete candidate)
  - Chargeback to departments
```

Cloud cost optimization isn't a one-time thing. It's a practice. Build it into your engineering culture: tag resources, review bills, right-size regularly.

Start with the low-hanging fruit: right-sizing and reserved instances. Those two alone typically save 40-60% for most companies.
